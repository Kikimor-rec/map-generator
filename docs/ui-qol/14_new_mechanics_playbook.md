# 14 — Playbook для новых механик (Design & Implementation Guidelines)

Дата: 2025-12-17

Этот документ — “правила расширения” редактора. Его цель: чтобы при добавлении новых механик:
- сохранялась консистентность UX,
- не ломались хоткеи/инспектор/undo,
- новые фичи были discoverable (их находят) и controllable (их можно контролировать).

---

## 14.1 Принципы UX для новых механик

### 14.1.1 Discoverability (находимость)
Новая механика должна иметь минимум 2 “точки входа”:
- через UI (кнопка/меню/панель),
- через command palette или контекстное меню (если применимо).

### 14.1.2 Predictability (предсказуемость)
- Она не должна менять данные “молча”.
- Если есть авто-поведение (например автроут), оно:
  - визуализируется превью,
  - подтверждается применением,
  - может быть отменено.

### 14.1.3 Non-destructive
- По умолчанию не удалять/не заменять “навсегда”.
- Предлагать “replace in selection”, “apply as new layer”, “snapshot”.

### 14.1.4 Consistency
- Если это действие над объектом — оно должно быть в inspector и в контекстном меню.
- Если это действие над сценой — оно должно быть в File/Generator панелях.

---

## 14.2 Состояния и “машина состояний” UI

Любая механика должна определить:
- В каких **mode** она доступна (Edit/Generate/Review).
- В каких **view** она корректна (Default/Print/VTT/Gameplay).
- Что происходит при:
  - Esc
  - смене инструмента
  - смене слоя
  - отмене (undo)

Рекомендация: для каждой механики писать короткий блок:
- “Entry” (как включить)
- “Active state” (что отображается/что можно делать)
- “Exit” (как выйти)
- “Persistence” (что сохраняется в проект)

---

## 14.3 Command system (обязательное правило)

Новая механика должна быть реализована как набор **команд**:
- `do()`: применить
- `undo()`: откатить
- `redo()`: повторить (если отличается от do, иначе do)
- `serialize()`: запись в историю (опционально, но полезно)
- `canExecute(context)`: валидатор

Причина: без этого ломаются undo/redo, макросы, повторяемость и тестируемость.

---

## 14.4 Инспектор и свойства

Если механика добавляет новый тип сущности или новые свойства:
- добавить schema (тип/поля/дефолты/валидация),
- добавить inspector UI:
  - одиночное редактирование
  - batch edit (если применимо)
- добавить отображение в object panel и фильтры/поиск.

---

## 14.5 Хоткеи и конфликт-менеджмент

### 14.5.1 Добавление хоткея
- Если действие частое → хоткей обязателен.
- Хоткей должен быть:
  - настраиваемый
  - независимый от раскладки
  - отражён в tooltip и help overlay.

### 14.5.2 Конфликты
- Нельзя “захватывать” Esc, Ctrl+Z, Ctrl+K и базовые camera controls.
- Если механика требует drag-модификатор:
  - использовать стандартные: Shift (ось/добавить), Alt (временно отключить snap), Ctrl/Cmd (дублировать/особый режим)
  - не вводить новый модификатор без причины.

---

## 14.6 Контекстное меню и object menu

Если механика влияет на объект:
- добавить пункт в контекстное меню соответствующего типа.
- если механика “локальная к точке” (например “Add junction here”) — она должна работать по ПКМ на точке/сегменте.

---

## 14.7 Визуальные подсказки и превью

### 14.7.1 Превью
Любая “авто” операция должна иметь:
- preview слой (неразрушающий),
- confirm/cancel,
- ясную подсветку того, что изменится.

### 14.7.2 Объяснение результата
После применения:
- toast/snackbar “что изменилось”
- кнопки: Undo, Open inspector, Export (если релевантно)

---

## 14.8 Валидация и ошибки

Новая механика должна определить:
- какие ошибки возможны,
- как пользователь их исправляет,
- какие “quick fixes” можно предложить.

Пример: “noPath” для коридора:
- quick fixes: уменьшить clearance / добавить waypoint / разрешить line jumps.

---

## 14.9 Экспорт/импорт и обратная совместимость

Если новая механика добавляет данные:
- они должны сериализоваться в проект JSON.
- необходимо предусмотреть:
  - migration (версия проекта)
  - разумные дефолты при отсутствии поля
- экспорт в изображение/печать не должен ломаться.

Если механика влияет на VTT экспорт:
- добавить соответствующие поля/валидаторы
- обновить VTT Preview overlay.

---

## 14.10 Производительность и деградация

Новая механика должна иметь план:
- что делаем в WebWorker (если тяжело),
- какой “simplified preview” при drag,
- как ограничиваем вычисления в live preview,
- как кэшируем.

---

## 14.11 Тесты и acceptance для каждой механики
Для каждой новой механики добавлять:
- 3–7 acceptance сценариев (ручных),
- 2–5 unit/integration тестов (если есть инфраструктура),
- 1 сценарий “stress” (на большой карте).

---

## 14.12 Шаблон чек-листа для PR/ревью
Перед мерджем новой механики команда отвечает “да/нет”:

- Есть entry points (UI + palette/menu)?
- Есть undo/redo?
- Есть inspector support (если свойство/тип)?
- Есть keybind или объяснение, почему нет?
- Есть preview/confirm для авто-операций?
- Есть serialization + версия проекта?
- Есть VTT/print implications?
- Есть performance plan?
- Есть acceptance критерии?

Этот чек-лист должен жить рядом с репозиторием и использоваться при code review.
